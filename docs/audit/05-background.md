# RunService — lifecycle & background audit

`RunService` is a foreground service whose only job is to keep an in-flight agent run alive while the app is backgrounded and to render it as an ongoing notification with a Stop action. It deliberately owns no domain state — the session store stays the source of truth — so it is `START_NOT_STICKY`, never resumes an interrupted run, and never persists anything itself. Its contract with the UI is three companion calls (`start`, `update`, `stop`) plus one result-notification helper (`notifyComplete`), and the run control seam `RunControl.stopHandler`, which is the only way the service can actually cancel work. It also holds a bounded `PARTIAL_WAKE_LOCK` that is re-armed on each progress update. The whole surface is defensive to the point of silence: nearly every platform call is wrapped in `runCatching`, which is what most of the findings below are about.

## Findings

| # | Severity | Finding | Line | Why it matters |
|---|---|---|---|---|
| 1 | P0 | `stop(context)` only calls `context.stopService`; the stop handler `RunControl.stopHandler` is invoked exclusively in the `ACTION_STOP` branch, so the "stop" seam stops the *service* and not the *run*. | 279–281 (vs 59) | The doc comment promises "Stop the run", but the run keeps executing with no foreground service, no wake lock and no notification. Without the FGS the OS is free to kill the process mid-run, so the in-flight run and its transcript are lost — and the user has lost their only handle on it. Unverified whether callers also invoke `RunControl.stop` directly. |
| 2 | P1 | `show()`'s `startForeground` failure path calls `stopSelf()` but neither invokes the stop handler nor clears the run; `markAlive(false)` only happens later in `onDestroy`. | 95–101 | A run whose FGS cannot start continues headless and invisible, with `alive` still `true` so `update()` keeps feeding a service that is tearing down. The user gets no signal that the run is now unprotected. |
| 3 | P1 | The `ACTION_STOP` branch never calls `startForeground`, so a STOP delivered to an instance created by `startForegroundService` returns and calls `stopSelf` without ever satisfying the 5-second duty. | 56–78 | Reachable when `start()` is issued and a Stop tap on a still-visible notification arrives first in the queue: the platform kills the process with `ForegroundServiceDidNotStartInTimeException` instead of a clean stop. |
| 4 | P1 | The stop handler call is wrapped in `runCatching { RunControl.stopHandler?.invoke() }` and the result is discarded, then `stopRun()` tears the notification and wake lock down anyway. | 59 | If the handler throws — or is `null` because the process was rebuilt — the user sees the notification disappear as if the run stopped while the run is still going. Nothing is logged and no error reaches the UI. |
| 5 | P1 | The wake lock is only re-armed from `show()`, i.e. only on `ACTION_UPDATE`, against a 5-minute timeout; there is no heartbeat or scheduled refresh. | 188–192, 214 | A healthy run that is silent for >5 min (one long build, a quiet provider stream) loses its `PARTIAL_WAKE_LOCK` and the device may suspend, stalling the very run the service exists to protect. Also, on expiry the field still points at the dead lock and the next refresh allocates a new `WakeLock` object while abandoning the old reference without releasing it. |
| 6 | P2 | `acquireWakeLock`/`releaseWakeLock` mutate the `@Volatile wakeLock` field with an unsynchronised check-then-act. | 165–179, 194–199 | `@Volatile` gives visibility but no atomicity: two concurrent callers can both pass the `isHeld` check and both acquire, leaking a lock until its timeout; the reverse interleaving releases a lock another thread just installed and nulls the field so the held lock is never released. |
| 7 | P2 | `runCatching { context.startService(intent) }` in `update()` swallows background-start denials with no log. | 271 | A dropped update means the shade keeps showing a stale progress line *and* never refreshes the wake lock, so the run silently degrades in doze. This is a failure the user needs to see, reduced to nothing. |
| 8 | P2 | The `else` branch (null intent, unknown action, redelivered command) posts a phantom "running" notification under the default title "Lumen". | 71–75 | Exactly the phantom row the `alive` flag was introduced to prevent: a notification with a Stop action whose handler is likely `null`, which only goes away when the user notices it. There is also no check that the intent came from our own app (service export status unverified — manifest not read), so a third party could start the service or fire `ACTION_STOP` at a live run. |
| 9 | P2 | `onDestroy` releases the lock and clears `alive` but never calls `stopForeground`, and posts no "interrupted" result notification. | 80–84 | Every non-`ACTION_STOP` termination path (`stop(context)`, `stopSelf` after a failed `startForeground`) relies on the platform to clean the ongoing row; if it lingers, the "running" text and its Stop action are stale. Combined with `START_NOT_STICKY` there is also no signal at all when a run is killed — a dead run looks like a hung one. |
| 10 | P2 | The fixed `NOTIFICATION_ID = 4711` shares one id namespace with `resultNotificationId() = sessionId.hashCode()`; the guard only bumps an exact 4711. | 205, 359–360 | A result notification can land on the ongoing run's id and replace the foreground notification (losing the Stop action and the FGS binding), or two sessions whose hashes collide silently overwrite each other's result row — the opposite of the "two sessions finishing at once" goal in the comment. |
| 11 | P2 | PendingIntent request codes overlap: `openAppIntent()` uses 0 while result notifications use the session's `hashCode()` as request code under `FLAG_UPDATE_CURRENT`. | 152, 349 | On a hash/0 collision the two PendingIntents are "equal", so updating the completion intent's `EXTRA_SESSION_ID` retargets the *ongoing* notification's tap as well — tapping "running" opens the wrong session. Silent and hard to reproduce. |
| 12 | P2 | Notification failures degrade to nothing: `ensureChannel` is fully swallowed and no `POST_NOTIFICATIONS` state is checked before building against `CHANNEL_ID`. | 114–129, 132 | On API 33+ without the permission (or if the user deletes the channel while running) `startForeground` succeeds with an invisible notification: the FGS runs, and the only Stop control the user had disappears. |
| 13 | P2 | `notifyComplete` wraps its entire body in `runCatching` with no fallback or log. | 305 | A denied notification permission or a channel error means the user never learns that the background run finished — and in particular never learns that it *failed*. A failed run is indistinguishable from a hung one. |
| 14 | P3 | `currentTitle` and `currentSessionId` are never reset in `stopRun`/`onDestroy`. | 63–64, 106–111 | A later `ACTION_UPDATE` or unknown-intent "running" notification resurrects the previous run's title and deep-link, pointing the tap at a session that is no longer running. |
| 15 | P3 | Notification polish: hardcoded English "Stop" label with icon `0`, deprecated `stopForeground(true)` boolean form, no `setForegroundServiceBehavior(FOREGROUND_SERVICE_IMMEDIATE)` for API 31+, and `durationLabel` renders 90 minutes as "90m 0s". | 141, 108, 334–340 | Localisation gap for the one user-visible control; on Android 12+ the FGS notification can be deferred up to ~10 s, which weakens the "run is protected" signal right when it matters; "90m 0s" reads as a bug. |

## Highest-leverage fix

Collapse every termination path — the `ACTION_STOP` branch, the companion `stop(context)`, `onDestroy`, and the failed-`startForeground` branch in `show()` — into one idempotent `teardown()` that (1) invokes `RunControl.stopHandler`, (2) removes the notification with `stopForeground(STOP_FOREGROUND_REMOVE)`, (3) releases and nulls the wake lock, and (4) clears `alive` and the stale title/session fields, with a `stoppedExplicitly` flag so a system kill does not double-fire the handler. Today the run-stopping responsibility lives only in one branch (line 59) while three other paths bypass it, which is the root cause of findings 1, 2 and 9: the service can die while the run lives on, unprotected and unstoppable. Routing everything through that single seam also gives one place to replace the silent `runCatching` blocks with logged, user-visible failures.
