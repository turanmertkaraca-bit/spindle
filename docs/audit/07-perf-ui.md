# LumenChatScreen — recomposition & main-thread audit

`LumenChatScreen` renders the whole chat surface: a `LazyColumn` transcript of grouped/deduped `MessageRow`s (keyed by step id, with linked tool runs drawn as a rail), a top bar with back/title/fork/files/shell/settings controls, a stack of notice/card composables above the composer (`ErrorNotice`, `HintNotice`, `UndoNotice`, `ChangesCard`, `TodoBoard`, `UsageMeter`, `AskCard`), the `Composer` itself, and two overlays (`FilePeekOverlay`, `QuickSettingsSheet`, `ModelPickerSheet`) plus a "latest" scroll cue. Audit covers lines 344–920 only; findings outside that range are not considered.

## Recomposition analysis

**Scope structure.** There is exactly one restart scope: the `LumenChatScreen` function body (344–910). Every parameter read inside it — `steps`, `input`, `busy`, `error`, `todos`, `changes`, `ask`, `quickSettings`, `modelPicker`, `followTail`, `cueArmed` — invalidates that single scope and re-runs the body top to bottom. Because `steps` is a streaming transcript, this means **the whole screen body recomposes once per streaming token**: the top-bar `Row` at 683–719 re-runs its `if (onFork != null)` branches, the notice chain at 819–835 re-evaluates `error`, `hint`, `lastRevert`, `changes.editCount`, `todos`, `usage`, `ask`, and both sheets at 871–908 re-evaluate their params. The only genuine skip boundary in the file is the `LazyColumn` item lambda at 736–789, which defers to item scope — and that boundary is punctured by findings #3 and #4.

**State reads and where they land.** `followTail` (`rememberSaveable { mutableStateOf(true) }`, 598) is *written* from a coroutine at 615 and *read* in composition at 795 — the read sits in the same scope as the transcript and composer, so scroll-position changes recompose the whole screen rather than just the cue. `cueArmed` (663) is correctly read only inside the effect at 665–671. The animated pulse is correctly *not* read in the body — the lambda at 548 defers the read to draw — but the lambda object itself is rebuilt each recomposition (see #3), so the optimization leaks through lambda identity. `forceOpenId` (572) and `lastAssistantId` (586) are `remember`ed but keyed on lists that change per token, so they recompute anyway.

**Hot-path allocations.** Per streaming token the body allocates: the `pulse` lambda (548), a `with(LocalDensity)` block (599), and on the visible-row path one `Modifier` chain per row with an `animateItem()`, a `then(...)`, a `padding(...)` and a `testTag("run-${step.id}")` interpolation (767–787). Downstream, `onAttach` (847), the QuickSettings `onOpenModel` wrapper (875–880) and four ModelPicker callbacks (901–907) are all new each token. Each of these is an unstable argument that suppresses skipping.

**Missing keys / wrong keys.** Keys are present and correct on the lazy items (`itemsIndexed(display, key = { _, s -> s.id }, contentType = { _, s -> s.kind })`, 736) — good. The problems are the opposite: *over*-keying. `forceOpenId` keys on `steps` *and* its own derivation `display` (572); backlinks key on the entire `steps` list when only paths/touched set matter (852). The activity-result launcher at 521 has *no* keys and therefore freezes its captured `onAttachImage`/`context`, which is the only place a key would actually be needed — though Compose offers no keying API there, so the correct fix is a `rememberUpdatedState` holder.

**Main-thread work in effects.** Two effects touch `listState.layoutInfo` synchronously and call `scrollBy`: the per-token effect at 618–637 and the per-layout effect at 644–657. They overlap in purpose and in target row, which is the one place in this range that looks genuinely janky rather than merely wasteful (#1). `snapshotFlow { listState.layoutInfo }` at 645 also re-emits on every layout pass, so the collector runs at layout frequency for the whole session, guarded only by `followTail`/`isScrollInProgress`.

**Not found in range.** No `key=` omission on lazy items; no state read inside a `drawBehind`/`Canvas` lambda that would invalidate layout; `flingBehavior` (513) and `listState` (512) are correctly remembered with no keys; `Bloom` is drawn in `drawBehind` (916–923) so its gradient work stays in the draw phase.

## Highest-leverage fix

Stop rebuilding the two row parameters that change on every token but carry no information: wrap the pulse lambda in `remember(value)` at 548 and hoist each row's modifier chain into a `remember(step.id, step.linkedAbove, colors)` (or move the `animateItem`/`drawBehind`/`testTag` chain into `MessageRow` itself, keyed on its own params) at 767–787. Today a streaming token produces a new `pulse` lambda and a new `Modifier` for *every* visible row, so `MessageRow`'s params are never equal and the lazy item skip at 736 is dead — every row in the viewport re-executes on each token. Restoring param stability is a two-line change with no behavioural effect and it converts per-token cost from "all visible rows" back to "the one growing row". Second-highest leverage, and cheap: drop `steps` from the key set at 572 and 852, and merge the two tail-pin effects (618–637, 644–657) into one so the bottom gap is corrected once per frame instead of twice.
