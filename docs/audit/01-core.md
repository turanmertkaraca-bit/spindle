# AgentLoop — core loop correctness audit

`AgentLoop.promptLocked` owns one run end to end: it takes a per-session mutex (line 140-143), finalizes any tool part left open by a previous turn (166), appends the user message (181), then loops `while (true)` (205) — each iteration snapshots durable history (213), evaluates the overflow policy and trims/compacts (216-245), builds the wire request (248-282), streams the provider with resilient retry while checkpointing partial text to the store (285-374), finalizes the assistant message with its tool calls (424-443), and either stops (no tool calls, LENGTH-continuation, step budget, doom loop) or executes each tool serially in call-index order (481-514) before repeating. The contract is "assemble → stream → run tools → repeat until the model stops asking"; the loop is the single owner of terminal state (`terminalState`, 179) and of the per-tool deadline (811-818), and it persists `RUNNING`/`IDLE`/`ERROR` around the whole run.

## Cancellation & timeout analysis

**What actually stops.** Cancellation is purely cooperative and observed at three points: `currentCoroutineContext().ensureActive()` at the top of each step (206) and before each tool in a turn (482), plus whatever the tool body itself awaits. `withTimeout(tool.timeoutMs)` at 817 cancels the child coroutine; it does not interrupt a thread. So the only things that stop are suspend points. A tool that sits in `Process.waitFor()`, `Files.readString`, `Thread.sleep` or a blocking socket is not interrupted — the timeout fires, the *coroutine* unwinds, and the underlying IO thread and child process keep running. The loop's `LoopToolContext.checkAborted()` (1111-1114) gives tools a way to cooperate, but enforcement lives in the tool, not the loop. Nothing in this file holds a `Process` handle or a `Thread`, so the loop structurally cannot kill what it did not create: **the tool process is not killed.**

The deadline is also optional: `if (tool.timeoutMs <= 0L)` at 814 runs the tool with no wrapper at all, so a tool that never returns holds the step, the session run lock and an IO thread indefinitely; the only escape is the parent's cancellation, which — per the above — still leaves the thread alive.

**Cancellation cleanup.** The `catch (e: CancellationException)` at 522 does its work inside `withContext(NonCancellable)`: it reads the in-flight assistant by id (525), computes `hasOpen` from PENDING/RUNNING tool parts (530-532), rewrites those parts to `state = ERROR, result = "aborted"` and the message to `finish = FinishReason.ERROR, error = "aborted"` (534-546), then emits the terminal state only if `terminalState == null` (550-552). The `terminalState` sentinel set at 179/418/518 is what prevents a double terminal `StateChanged`, and it works: a cancel during the final `persistState(IDLE)` skips the re-emit and only persists. The `finally` at 566-576 then runs `store.maintain()` and `snapshots?.pruneBounded()` in its own `NonCancellable` block. Note the ordering — the catch's `NonCancellable` block runs *before* the `finally`, and both run before the `CancellationException` is rethrown at 554, so the run lock at 141 is released only after cleanup. Good design.

**Timeout vs. real cancel.** At 820-830 a `TimeoutCancellationException` is disambiguated by `currentCoroutineContext().ensureActive()` before being blamed on the tool — so a parent Stop propagates through 831-832 instead of being reported as a timeout. Two gaps: a tool's *own* internal `withTimeout` also surfaces as `TimeoutCancellationException` and is mislabelled with the loop's message and `timeoutMs` metadata; and if the parent cancels in the same instant as the deadline either branch can win, so a Stop can still be reported as a timeout in the narrow race.

**Can the loop wedge in a busy state?** Yes, four ways: (a) `agent.maxSteps == null` → `while (true)` with no total cap; (b) a permission ASK or `questionGate.ask` with no timeout (781, 1104); (c) `tool.timeoutMs <= 0` → no deadline at all; (d) after a timeout the abandoned tool coroutine may still call `bus.emit`, `ctx.setTodos` or write files *after* the loop wrote its `[timeout]` result and moved to the next step — a concurrent writer racing the next turn's reads with no synchronisation. In all four the session sits RUNNING and the per-session `Mutex` at 140 is held, so every later prompt for that session blocks behind it.

## Highest-leverage fix

Make the tool boundary a *supervised, forcibly-reclaimable* unit instead of a `withTimeout` wrapper. Run each tool in a child `Job` the loop owns, hand the `ToolContext` a registry that tools register their spawned `Process`es with, and on timeout or parent cancellation (1) cancel the job, (2) destroy any registered processes, (3) wait a short bounded grace period for actual termination, and only then (4) write the result part and advance the step — refusing to report `DONE`/`ERROR` while the job is still alive. That single change closes the P1 "reported cancelled but still running" hole, removes the abandoned-coroutine races on the store and bus, and makes "timeout" a truthful state. Pair it with a cheap second fix: default `agent.maxSteps` to a finite number (and clear `recentSignatures`/reset `continuations` per step) so the loop always has an exit that does not depend on the model's cooperation.
