# AndroidDatabase — persistence integrity audit

`AndroidDatabase` owns the single lazily-opened SQLite handle for `lumen.db`: it opens and integrity-checks the file, quarantines a corrupt one and starts fresh, installs connection pragmas (`busy_timeout`, `foreign_keys`, WAL, `synchronous=NORMAL`, page cache), runs the six-step `user_version`-gated migration chain that builds and reshapes `sessions`/`messages`/`parts`/`todos`/`snapshots`/`snapshot_blobs`, and provides the `lease()` refcount so a concurrent `close()` cannot free the handle underneath an in-flight query. It is the only place that knows about schema versions, so every durability and upgrade guarantee in the app rests on this file.

## Findings

| # | Severity | Finding | Line | Why it matters |
|---|---|---|---|---|
| 1 | P0 | `quarantine()` runs whenever `openOrCreateDatabase` returns null, not only when integrity fails — a transient open failure (disk full, EACCES, too many open files) renames a healthy DB to `.corrupt-<ts>` and creates an empty one | 77–93 | The user opens the app to an empty history and has no signal that the data still exists on disk; a recoverable I/O blip is converted into apparent total data loss |
| 2 | P0 | A throwing migration is never caught: `db()` leaves `opened` unassigned and unclosed, so the handle leaks and every subsequent `db()` call re-runs `openHealthy()` → `migrate()` → throws "again" | 42–47, 124–135 | The failing version is never passed, so the app is permanently unusable on that install; there is no quarantine/fallback path for "migration failed" the way there is for "file corrupt", i.e. exactly the launch crash-loop the KDoc claims to prevent |
| 3 | P1 | `refs` is only incremented by `lease()`; a caller using `db()` directly is invisible to the refcount and `close()` will free its handle mid-query | 38–48, 55–67, 364–375 | The "safe from any thread" contract is a convention with no enforcement — a direct `db()` user gets `IllegalStateException: attempt to re-open an already-closed object` instead of a lease-protected handle |
| 4 | P1 | TOCTOU between the two `closed` checks: `lease()` increments `refs` and releases the monitor, then the block's `db()` re-checks `closed` and throws even though a valid handle is pinned and `refs > 0` | 56–59 vs 39–40 | A lease acquired just before `close()` fails with "database is closed" mid-block; the refcount protects the handle from being freed but does not make the lease usable, so the error is misleading and the lease guarantee is only half-true |

## Migration safety

The per-step structure is correct in the way that matters most. Each `Migration` is applied as:

```kotlin
db.beginTransaction()
try {
    migration.applyTo(db)
    // The stored version commits atomically with the DDL above.
    db.rawQuery("PRAGMA user_version = ${migration.version}", null).use { it.moveToFirst() }
    db.setTransactionSuccessful()
} finally {
    db.endTransaction()
}
```

`user_version` **is** set inside the same transaction as the schema change — the assignment at line 130 executes before `setTransactionSuccessful()` at line 131, and `PRAGMA user_version` is stored in the database header page so its write participates in the transaction. A failure in `applyTo` skips `setTransactionSuccessful`, `endTransaction` rolls back both the DDL and the bump, and the DB stays at the previous version. The comment at lines 14–16 and 109–113 is therefore accurate *per migration*: there is no half-upgraded single step.

There is also no outer transaction spanning all pending migrations, so a v0 database interrupted after step 3 commits as a consistent v3 database and resumes at step 4 next launch. That is the right trade-off and is not a bug.

What is not safe is everything around that inner block. (a) A migration failure is not contained: `migrate()` is called from `db()` at line 43 with no `try`/`catch`, so the exception escapes with the newly opened handle neither stored in `database` nor closed — the leak in finding 2 — and the next `db()` call retries from the same version forever. A "partially upgraded DB" in the sense of mixed versions is not reachable, but a *stuck* DB is. (b) Several steps assume tables/columns that may be absent rather than probing first: migration 3 needs `snapshots` (line 258–269) and migration 2 needs `messages.seq` (line 235–247); migrations 5 and 6 do guard (`columnNames` checks at 215 and 321), so the asymmetry is the smell. (c) The version bump goes through `rawQuery` — a *read* API — and relies on `moveToFirst()` to step a write statement; if the statement is ever created but not stepped (or the cursor fill no-ops), `setTransactionSuccessful()` would still commit the DDL without the bump and the next open would replay an `ALTER TABLE ADD COLUMN`, which is not idempotent and would fail with "duplicate column name". That specific path is unverified — a test asserting `user_version` advances after each step would settle it. (d) `DROP TABLE IF EXISTS _message_seq` at line 235 omits the `TEMP` keyword while the table is created as `CREATE TEMP TABLE`, so name resolution spans both schemas; and temp-table changes do not always roll back cleanly with the enclosing transaction, which can leave the scratch table behind after a failed v2 — unverified, and harmless only because the next run drops it first.

## Highest-leverage fix

Separate "the file is corrupt" from "the open or the upgrade failed". In `db()`, wrap `openHealthy()` + `migrate()` + `checkpoint()` in a `runCatching`/`try`-`catch` that closes the candidate handle on any failure and leaves `database` null, so a failure neither leaks a connection nor silently resets `user_version`; escalate to `quarantine()` only when `integrityOk` actually returned false, and when the open itself failed for an I/O reason, rethrow or surface a distinguishable "storage unavailable" state instead of replacing the user's history with an empty file. Then close the lease gap in the same pass: have `lease()` return the already-opened, refcounted `SQLiteDatabase` (checking `closed` once, under the monitor, at the moment the handle is pinned) so the block cannot be refused after the lease is granted, and stop exposing a bare `db()` that bypasses the refcount — or make `close()` refuse to free the handle while any direct borrower exists. Finally, set the version with `execSQL("PRAGMA user_version=$n")` and assert the stored version after each step so an upgrade that commits DDL without committing its version fails loudly at the migration instead of at the next launch.
