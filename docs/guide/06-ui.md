## Design tokens

`LumenTokens.kt` is the single source for colour, spacing, radius, type and
duration. **Do not introduce a literal** that a token already expresses. Known
token-literal drift is a listed Run D item; when you touch a screen, replace
literals with the existing token rather than adding a new one.

## Known problems (from `docs/audit/07-perf-ui.md`)

These are real and still open unless `PROJECT-STATUS.md` says otherwise:

- **`LumenChatScreen` recomposition** — the audited findings include double
  work per frame and unstable lambdas. This file is the reason the UI pass
  exists; treat any change here as perf-sensitive.
- **Inconsistent chrome language** across screens — Run D is a
  minimal/merged/coherent pass, so resist adding a new visual idiom.
- Composable-heavy files compile and test **only on CI** (Robolectric).

## Rendering the agent state

`StepMapper` converts `AgentEvent`s into `UiStep`s. Two invariants that the loop
guarantees and the UI relies on:

- No tool part stays `PENDING` after a run ends (the loop rewrites them to
  `ERROR` on every abort path). If you see a permanent spinner, the bug is in
  the loop's exit path, not in the UI.
- `PartReset` clears the text/reasoning builders, so a retry does not
  concatenate attempt 1 and attempt 2.

## Working on the UI without a device

`:app` has no preview harness that runs in the dev sandbox. Compile
(`:app:compileDebugKotlin`) is the local check; behaviour needs CI. Do not claim
a UI change is verified on the strength of a local build — see
`07-testing.md`.

## Motion: the safety rule (read before adding any animation)

**No animation may loop faster than 1 cycle per second, and every loop must be
disabled by reduce-motion.**

This is a safety requirement, not a style choice. The owner's words: *"won't
trigger some people's seizures every time the AI writes"*.

### The enforcement points

| Thing | Where | Rule |
|---|---|---|
| The rules themselves | `ui/MotionPolicy.kt` | pure Kotlin, JVM-tested |
| Platform reduce-motion read | `platform/AndroidSystemMotion.kt` | animator **and** transition scale |
| The scale→boolean arithmetic | `ui/SystemMotion.kt` (`DurationScale`) | minimum of the two |
| The pulse spec | `ui/LumenMotion.pulse(periodMs)` | **a function**, clamps to the floor |

`LumenMotion.pulse` used to be a `val` holding a bare 1400 ms
`infiniteRepeatable(..., RepeatMode.Reverse)`. Because it was a constant, every
call site inherited it and no caller could be prevented from choosing a fast loop.
It is now a **function**: the period is a required argument and
`MotionPolicy.safeLoopPeriod` raises anything under 1000 ms to 1000 ms.

Current streaming pulse: **2000 ms**, opacity **0.62 → 1.0**. A slow, low-amplitude
breath — never a flash.

### Under reduce-motion

- `MotionPolicy.streamingPulsePeriodMs` returns **null**, and the caller does not
  create the `rememberInfiniteTransition` at all. A loop that still schedules
  frame callbacks while drawing identical pixels is a battery bug, not just a
  cosmetic one, so "not animating" has to mean "not ticking".
- `MotionPolicy.pulseAlphaRange` returns the constant `1f to 1f`.
- `MainActivity.animatedColors` skips the 420 ms theme cross-fade
  (`reduceMotion` → return the target palette immediately).

### Where the user's setting comes from

Android has no `Settings.Secure.REDUCE_MOTION`. The switch the user flips —
Accessibility → *Remove animations*, or Developer options → *Animator duration
scale* — surfaces as `Settings.Global.ANIMATOR_DURATION_SCALE` and
`TRANSITION_ANIMATION_SCALE`. `AndroidSystemMotion` reads both and
`DurationScale.reduceMotion` takes the **minimum**, because either channel being
0 is the user asking for no motion.

`KeyStore.reduceMotion` **defaults to the system value, not `false`**:

```kotlin
get() {
    if (prefs.contains(KEY_REDUCE_MOTION)) return prefs.getBoolean(KEY_REDUCE_MOTION, false)
    val seeded = systemReduceMotion?.invoke() ?: false
    prefs.edit().putBoolean(KEY_REDUCE_MOTION, seeded).apply()
    return seeded
}
```

It seeds **once**. A user who deliberately turns the app's own toggle back on is
not overridden by the system flag on the next launch — an explicit choice wins
after the first read.

### When you add a new animation

1. If it loops, it must go through `MotionPolicy.safeLoopPeriod`.
2. If it is non-essential (ambient, decorative), it must be off when
   `reduceMotion` is true.
3. Add a case to `app/src/test/kotlin/dev/lumen/app/ui/MotionPolicyTest.kt`.
   That test is plain JVM — it runs in CI *and* locally, unlike `:app`
   Robolectric.

## The transcript scroll rule (read before touching the timeline)

**Never call `scrollBy` / `scrollToItem` from inside a
`snapshotFlow { listState.layoutInfo }` collector.**

That was `FREEZE-01`, and it is the worst bug this app has had: scrolling
invalidates layout → layout changes `layoutInfo` → the collector fires → scrolls
again, forever, on the main thread. Android showed "app has stopped working", and
the reader was teleported mid-transcript because every partial layout pass issued
another corrective scroll.

### How it is structured now

`ui/ChatScrollPolicy.kt` (pure Kotlin, 15 JVM tests) owns the decisions:

| function | answers | returns |
|---|---|---|
| `shouldFollow(...)` | is the reader at the tail? | **`Boolean?`** — `null` = inconclusive, keep the current value |
| `correction(...)` | how far to move? | `None` / `JumpToLast` / `ScrollBy(delta)` |

The three properties that make it quiescent:

1. **`None` covers "already aligned" AND "empty space below a short tail".** A
   positive gap cannot be fixed by scrolling — treating it as a correction is what
   made the old loop unable to converge.
2. **`shouldFollow` is tri-state.** An in-flight gesture, or an ambiguous
   near-the-end measurement, returns `null` so the caller keeps its belief. Do not
   flatten this to a `Boolean`; doing so was a real regression (`e487e6b`).
3. **`pinnedOnce`.** Before the first pin the list is at the top only because
   nothing has scrolled it — not because the reader chose to be there. Without this
   flag the decision **latches**: not following → won't pin → stays at top → still
   "not following", so the chat never follows a streaming answer.

### Keying

The pin effect keys on `(listState, count, lastBodyLength)`. `count` alone is not
enough: a single assistant Part only ever **grows**, so a long streaming answer
never changes the item count. Keying on the last row's body length re-arms the
effect when text arrives, not on every frame.

### The "↓ latest" cue

Shown whenever `!followTail`. Because `shouldFollow` only returns `false` when the
reader has genuinely scrolled up (and `pinnedOnce` is true), the cue cannot appear
on a fresh chat.
