## Design tokens

`LumenTokens.kt` is the single source for colour, spacing, radius, type and
duration. **Do not introduce a literal** that a token already expresses. Known
token-literal drift is a listed Run D item; when you touch a screen, replace
literals with the existing token rather than adding a new one.

## Known problems (from `docs/audit/07-perf-ui.md`)

These are real and still open unless `PROJECT-STATUS.md` says otherwise:

- **`LumenChatScreen` recomposition** — the audited findings include double
  work per frame and unstable lambdas. This file is the reason the UI pass
  exists; treat any change here as perf-sensitive.
- **Inconsistent chrome language** across screens — Run D is a
  minimal/merged/coherent pass, so resist adding a new visual idiom.
- Composable-heavy files compile and test **only on CI** (Robolectric).

## Rendering the agent state

`StepMapper` converts `AgentEvent`s into `UiStep`s. Two invariants that the loop
guarantees and the UI relies on:

- No tool part stays `PENDING` after a run ends (the loop rewrites them to
  `ERROR` on every abort path). If you see a permanent spinner, the bug is in
  the loop's exit path, not in the UI.
- `PartReset` clears the text/reasoning builders, so a retry does not
  concatenate attempt 1 and attempt 2.

## Working on the UI without a device

`:app` has no preview harness that runs in the dev sandbox. Compile
(`:app:compileDebugKotlin`) is the local check; behaviour needs CI. Do not claim
a UI change is verified on the strength of a local build — see
`07-testing.md`.
